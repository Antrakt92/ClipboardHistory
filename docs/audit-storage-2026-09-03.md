# ClipboardHistory storage audit — 2026-09-03

Baseline: `b7aeac62a22b4c2ecbe7edbef50d9e63088f85a0`. This second pass covers SQLite storage, retention transactions, compaction, and legacy database migration. All database fixtures were temporary and synthetic. No existing user history, clipboard contents, logs, or autostart configuration were read or modified.

## Findings and changes

1. **History metadata queries traversed image payloads.** The schema stores `image_hash` and `truncated` after `image_data`. Fetching those later fields required SQLite to traverse large overflow records even though the query did not return the BLOB itself. The popup never used `image_hash`; that field is removed from `get_history()`. Truncation is read only for text rows using `CASE`. Full-entry/image access and deduplication remain available through their existing methods; the schema is unchanged.
2. **A tiny deletion could trigger a full database rewrite.** After the existing daily interval, deleting a 2 MiB item from a 240 MiB history caused a roughly three-second `VACUUM` and blocked history reads. Compaction now requires both at least 32 MiB of free pages and at least 25% free pages. Small gaps remain reusable by SQLite. The daily limit still applies. These are application maintenance thresholds, not SQLite correctness requirements.
3. **Retention was committed separately from new entries and pin changes.** An insert was committed before retention cleanup; a later cleanup failure left a new row despite a failed operation. Unpinning had the same partial-state problem. Text/image insertion, cap cleanup, and expiration now share one transaction. Unpinning and cap cleanup also commit together. Rollback restores maintenance flags and expiration timing. A full-history insertion now commits once instead of twice.
4. **Legacy migration could publish a stale database without its WAL.** The old path moved/copied the main database first, then attempted sidecar moves, and swallowed errors. The regression produced a destination missing the table and committed row still present in the source WAL. Migration now uses SQLite's backup API from a read-only source into an owned temporary database, validates integrity, produces a standalone snapshot, closes it, and publishes with a Windows rename that refuses to overwrite an existing destination. Errors propagate so startup cannot silently switch to an empty history.

Successful migration deliberately retains the legacy database family as a recovery copy. It is not live-synchronized with the new history and is not removed by clearing entries in the new database. Automatic source deletion is outside this change. Failed migration preserves the original files and removes only its own staging files where the filesystem permits cleanup. Repeated busy/locked backup callbacks are limited to approximately three seconds; total backup progress is limited to thirty seconds before aborting safely. A single blocking filesystem call cannot be interrupted by this callback limit.

## Synthetic performance results

The workload contains 120 image-sized BLOBs of 2 MiB each: 240 MiB of payload. These are generated bytes, not user screenshots or a PNG decoding benchmark. Python 3.13.15 and SQLite 3.50.4 were used on Windows. Each version used the same schema and locally installed runtime. Five alternating open/query/integrity samples used a recently created local fixture, so results are cache-warmed measurements, not cold Windows sign-in timing. Compaction scenarios ran once per version on separate copies of the same fixture.

| Metric | Baseline | Updated |
| --- | ---: | ---: |
| `get_history(50)`, median | 70.756 ms | 0.170 ms |
| `get_history(50)`, observed range | 66.174–75.090 ms | 0.162–0.252 ms |
| Complete database open, median | 166.161 ms | 182.226 ms |
| Full integrity check, median | 182.425 ms | 171.882 ms |
| Compaction after deleting one image, 0.83% free | 3073.526 ms; VACUUM ran | 0.085 ms; VACUUM skipped |
| Concurrent history call during that compaction | 3030.882 ms | 0.875 ms |
| Compaction after deleting sixty images, 50% free | 1540.523 ms | 1620.737 ms |
| Concurrent history call during substantial compaction | 1506.040 ms | 1509.652 ms |

No database startup speedup is claimed: full integrity validation remains enabled and open/check timings vary. The measured improvement concerns metadata reads and avoiding unnecessary full-file compaction. Large eligible compaction remains synchronous and can still block the UI; this portion of `CH-AUDIT-021` remains open. The metadata timings exclude thumbnail/image decoding and are not total popup rendering times.

Exact samples are saved in [storage-benchmark-2026-09-03.json](storage-benchmark-2026-09-03.json). Reproduce with:

```powershell
python tests/benchmark_storage.py b7aeac62a22b4c2ecbe7edbef50d9e63088f85a0 --rows 120 --image-mib 2 --runs 5
```

The helper creates and removes only its temporary fixtures and prints JSON. Its payload cap is 256 MiB; fixture copies, WALs, and SQLite's compaction workspace need additional temporary disk space. It does not open the real application database or start application services.

- Confirmed failures before implementation covered partial insert/unpin persistence, two-commit retention, unused hash reads, tiny-deletion compaction, corrupt migration input, failed publication, and committed WAL contents missing from the published destination.
- Additional regressions cover compaction thresholds, maintenance-state rollback, source/WAL snapshot consistency, a destination created concurrently with migration, staged integrity failure, and backup timeout cleanup.

Legacy migration and size/cap transactions were exercised against disposable SQLite databases, including a source connection with uncheckpointed committed WAL data.
